# Proposal 应用验收指南

验收针对保存的完整研究会话。自动检查只证明日志、状态和来源记录满足协议；是否答对、是否理解追问、来源是否支持解释仍需人工检查。scripted fixture 可以验证工程控制流程，不能作为真实模型应用验收成功的证据。

每个场景保留请求、session ID、episode/report 版本、模型执行模式、来源快照、工具/模型调用日志、预算与停止原因。先做自动记录检查，再由真人填写语义判断；失败、不支持和未完成均如实保留。空白记录位于 [application-acceptance.template.json](../examples/study/application-acceptance.template.json)。

| 场景 | 自动日志可检查项 | 必须人工判断项 |
|---|---|---|
| 关闭后重开并继续 | session ID 连续；旧报告版本/哈希不变；来源、计算、依赖版本可重新读取；新 episode 有独立且有限的预算 | 是否保留用户任务、范围和关键上下文；是否能自然继续研究 |
| 解释已有结果 | 引用了目标历史报告或现有证据/公式；没有使用 stale 依赖；复用/新增调用可追溯，计数完整 | “这个结果为什么”是否指向正确的公司、期间和结论；是否解释计算或证据，而非复述无依据理由；额外取数是否必要 |
| 增加公司比较 | 当前范围同时保留原公司和新公司；必答清单包含比较要求；新证据及计算可定位 | 是否比较同一指标、期间/财季、币种、会计与业务口径；不能比较的地方是否明确说明 |
| 修正财季/指标/截止时间 | scope/version 更新；受影响旧结果标记过期；重新取数/计算与新报告可追溯；历史报告原文不变 | 是否正确理解“改为”而非追加；新答案是否完全用正确期间/定义；旧结论是否残留并误导 |
| 开发之外的发行人 | 身份发现记录、来源 URL/快照与调用路径存在；无公司专用固定答案；执行模式明确 | 实际解析的发行人是否正确；研究路径是否通用；新公司的披露、财季和业务结构是否被正确处理 |
| 当前数据覆盖之外的请求 | 缺失/失败工具结果、尚未回答项与 partial 状态保留；预算停止有原因；没有捏造来源或直接宣布完成 | 是否清楚说明能回答和不能回答的范围；是否合理尝试可用替代来源；不能由一次查询失败推断整份文件或全部来源不可用 |

未见发行人场景的“通用路径正确”和“线上资料实际能取到”分别记录。离线没有该来源时，正确披露限制属于失败处理测试，不等同于完成新发行人的真实研究验收。

建议记录三种独立结论：`automatic_log_status`（pass/fail/not_run）、`human_semantic_status`（pass/fail/unassessable/pending）、`execution_mode`（实际输出的 mode）。只有日志检查通过而人工判断待做时，不得标“应用验收通过”。模板不会自动填写任何真人姓名或成功结果。

可使用 root 提供的 acceptance CLI 检查保存日志完整性；本指南不替代其检查输出，也不重复实现检查器。真实模型、真实新发行人联网可用性和真人语义验收须由后续实际运行完成。
