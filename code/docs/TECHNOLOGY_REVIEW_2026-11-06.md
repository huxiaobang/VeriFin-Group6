# VeriFin 技术选型复核（2026-11-06）

本次结论：**整体方向可保留，但技术选型还没有充分闭环；优先补齐财报结构、跨语言检索和实验口径，比直接换一个更大的 embedding 或换 Agent 框架更有价值。** 小 embedding 可能漏证据，不过“模型小所以整个 Agent 很蠢”并不是足够准确的诊断。结构已经丢失、查询语言不匹配、期间选错、检索结果缺乏支持判定，都可能产生同样的现象。

本报告依据当前 `verifin/` 源码、已提交 [Proposal](PROPOSAL.md) 和下列一手资料。它是选型与差距记录，不替代真实模型实验，也没有修改已提交的 Proposal。主模型接入和本地 embedding 实测由同期工作单独记录；这里不提前宣布任何模型胜出。官方资料检索日期为 2026-11-06。

## 1. 建议保留和需要补研究的选择

| 部分 | 当前实际实现 | 建议与理由 | 还缺的证据 |
|---|---|---|---|
| 财务数字 | SEC Company Facts；明确概念、单位、期间、来源及累计值推导限制 | 保留结构化事实作为数值主路径。财务计算不依赖文本向量相似度来决定数字 | 新发行人、重述、不同 taxonomy、同义概念并存的真实访问检查 |
| 解释性披露 | replay 文本及 SEC primary HTML；可定位原文片段 | 保留，但将“文本抽取”与“表格语义读取”明确分开。逐步补结构化 HTML 表格 | 行列、复合表头、脚注、非 GAAP 和分部数据的保存及定位 |
| 分块 | 按字符上限切分，偏好段落/句子边界并重叠 | 作为透明基线；下一版优先结构边界和 tokenizer 限额，保留来源映射 | 不同块长的召回、表头完整性、重复上下文比例 |
| embedding | 新查询本地编码、缓存及冻结向量已实现；三种真实模型已做共同语料开发诊断 | 小模型只作资源基线；优先继续检验 Qwen0.6B 的跨语言质量，不按参数量直接定案 | 更多独立问题、复杂表格及正式 held-out；当前测量见 [实测报告](EMBEDDING_STUDY_2026-11-06.md) |
| 检索融合 | BM25、精确 cosine、等权 RRF，k=60 | 保留 BM25 与 dense 的配对比较；hybrid 是否作为默认由开发实验决定 | 英文、跨语言、数字/期间混淆、表格问题的分层结果 |
| reranker | 尚未实现，Proposal 可选 | 先检查正确证据是否已进入候选集；候选召回足够而排序差时再加 | rerank 前后召回/排序、CPU 延迟、额外内存；不能假定必然提升 |
| 向量索引 | 小语料上全量精确排序 | 当前无需为了“像生产系统”引入向量数据库；必要时先做矩阵化精确检索 | 实际语料增长后的延迟/内存，而非预设必须上 ANN |
| 编排 | Python 状态机，模型分角色调用，工具受控执行 | 保留 Proposal 明示的 fallback；是否为 Agent 取决于观察后规划和多轮行为 | 真实模型如何应对失败、澄清、改范围、证据失效 |
| 记忆 | SQLite 保存会话/证据/计算/报告版本；近期加词项相关历史选择 | 保留显式研究状态；不要把历史摘要当事实来源 | 长对话指代、更正覆盖旧要求、旧报告解释及重开后连续性 |
| UI 与图表 | 本地单用户 HTTP/JS/SVG，非 Streamlit/Plotly | 当前用途可保留；报告如实记录实现偏离和原因，无需为框架名称重写 UI | 实际同学上手测试；不是多用户部署、后台研究服务 |
| 核验与评估 | 规则＋Structured Critic；E1/E2/E3 管线 | 保留事实、引用、计算、语义支持及完整性分离的设计 | 自然模型输出与独立判断；单元测试不提供效果提升结论 |

上述“建议”是基于项目规模和源码的工程判断；“当前实现”不等于已经通过真实模型有效性验证。

## 2. 财报摄取是目前比模型大小更明显的薄弱点

SEC 的 XBRL 聚合 API 覆盖标准 taxonomy、适用于整个申报实体的事实。这支持我们把它作为合并财务数字入口，也意味着不能把 Company Facts 解释为“能完整提供分部、自定义指标和所有表格”。SEC 还说明不同公司的财历可能不同，calendar frame 不是无条件可比的财季。[SEC EDGAR APIs](https://www.sec.gov/search-filings/edgar-application-programming-interfaces)

代码已经避免把全年/YTD 默认为单季，也拒绝用 EPS 或加权平均股数的累计值相减来推导单季。这些保守约束应保留。需要继续区分：

- **可核验数字**：明确标签、单位和起止日期的 XBRL 数值；计算由确定性函数执行。
- **解释性陈述**：管理层对原因的归因、财报叙述、脚注；须保存原文并由 Critic 检查支持程度。
- **当前未完全支持的结构**：分部表、复杂多层表头、定制 taxonomy、一般 PDF 附件；不能靠 embedding 自动补成结构化事实。

现有 `tools.py::_FilingText` 将可见 HTML 文本的所有空白压为单空格。可复现诊断中，一个含 `USD millions / 2025 / 2024` 表头、收入 `100 / 90` 的两年表变成：

```text
USD millions 2025 2024 Revenue 100 90
```

这说明保存了词与数字，却没有保存单元格关系；换更大的 embedding 不能保证恢复被丢失的关系。应先做一个独立的结构抽取层，保留段落/标题、表格 ID、行列、表头、脚注及原始 HTML/文档快照定位；复杂合并单元格无法可靠解析时保留整表并显示限制。旧字符 offset 应继续可重现，不能在原来的提取版本上悄悄换文本。

对于需要 PDF 的扩展，**Docling 是值得试验的候选，而非现在必须引入的依赖**。其文档说明分块可结合文档结构和 token 限额，并支持表格跨块重复表头。可先在现有来源的少量复杂表上做离线对比；若原生 HTML/XBRL 已满足需求，没有理由让所有文档都经过 OCR/VLM。[Docling chunking](https://docling-project.github.io/docling/concepts/chunking/)

现有事实选择策略是 `latest_public_filing_at_cutoff`。这是可解释的默认策略，但与“当时首次公布的数值”不同。正式研究应在案例中写明截止时间及口径，遇到重述时展示原始/修订来源；不要把较新的重述值误当为历史市场已知信息。

## 3. 检索要测一整条链，不能只比较 embedding 的参数量

### 3.1 跨语言与财务区分能力

用户可能中文提问，而财报为英文。当前 BM25 tokenizer 对 `收入为什么增长` 返回一个完整中文 token；它既不是中文分词，也不做中英语义匹配。即使补中文分词，也不能凭词项直接匹配英文 `revenue growth`。因此实际候选应比较：原语言的多语言 dense、原英文查询的 BM25，以及可追踪的英文查询改写＋hybrid。最后一种会增加模型调用和语义漂移风险，若采用须同时保存原问题、改写及成本；本轮不把它当已实现能力。

检索测试必须含容易误召回的相邻概念，例如 Cloud gross margin 与 consolidated operating margin、季度与全年、当期与上年，以及“原因”“数值”“定义”三种不同证据需求。普通英文关键词的命中不能证明能处理这些区别。

### 3.2 分块和上下文预算

现有默认字符分块 1800/250 与本地 encoder 配置中的 600/80 都只是可重复的配置，不是验证出的最佳值。字符数也不等于 token 数。建议先以一份所有候选均能完整编码的共同语料比较模型，再对候选模型单独比较块长；不允许某模型静默截断输入后仍报告“相同语料”。

更小的块可能更容易定位主题，但缺失单位/表头/前置限定；更大的块保留上下文，却可能把多个不同指标混进同一向量。可以评估“短块检索＋相邻原文扩展”，但扩展内容必须计入给 Researcher 的总预算，保留对应的原文范围。

### 3.3 Hybrid 与 reranker 的合理位置

现有 RRF 避免直接相加 BM25 和 cosine 的不同量纲，作为基线合理。RRF 原论文的 k=60 来自其先导实验；这不是它对所有财报任务最优的证明。先用固定值完成可解释比较，只有开发数据足够时再调参，正式测试不可边看结果边选权重。[Cormack et al., SIGIR 2009](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf)

Cross-encoder 会同时读取 query 与候选 passage，适合作为第二阶段排序器。它的作用范围是候选集，不能找回第一阶段根本没召回的证据；此外相关性高仍不等于支持某个金融结论。建议先记录 Recall@候选数，再决定是否做 reranker 试验，避免无根据增加推理负担。[Sentence Transformers: Retrieve & Re-Rank](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

### 3.4 目前不需要先上向量数据库

当前 replay 的语料很小。精确 cosine 可以作为质量基准，不引入近似搜索造成的漏召回；若将来 Python 循环成为瓶颈，先比较 NumPy 矩阵乘法或 FAISS Flat，再根据真实延迟和内存选择 ANN。FAISS 文档将 Flat 作为精确基线，并提醒少量查询时构建复杂索引未必合算。[FAISS index selection](https://github.com/facebookresearch/faiss/wiki/guidelines-to-choose-an-index)

这不是拒绝扩展：当新增发行人/文档使精确检索超过已约定延迟，或需要持久索引、共享服务和并发运维时，再比较 HNSW/IVF 或数据库。比较必须含过滤后召回、删除/重建、索引与源快照版本绑定，不能只看无过滤的搜索速度。

## 4. E3 口径复核与本轮处理

当前开发文件有 14 条查询，10 条有相关片段，4 条是工程负例；标注已明确不是独立 gold，而且正例没有穷尽所有替代支持片段。因此它适合发现接线、过滤和明显检索错误，**不足以锁定最终模型，也不能支持“金融检索普遍提升多少”**。

| 问题 | 影响 | 具体处理 |
|---|---|---|
| 原 `negative_empty_accuracy` 混合过滤为空与非空语料无关问题 | dense 没有拒答阈值，非空语料总会返回 top-k；与只返回正 BM25 分数的行为不同 | 本轮已增加负例类别及分项返回率、旧字段解释；不纳入 embedding 排名。语义拒答仍需单独定义统一协议 |
| recall 要求一个 passage 完全覆盖标注 span | 块边界变化可能导致标注不可覆盖；这不是模型变差 | 比较前验证覆盖率；跨分块实验另报标注可覆盖率，并保留相同原文 gold，不能为某模型缩短标注 |
| E3 ranking latency 只计过滤和排序 | 排除了模型加载、query encoding、文档编码、磁盘读取；不能代表用户等待 | 本轮实测另外报告加载、建索引、query encoding、RAM；runtime 记录缓存与编码时间。完整交互延迟仍需真实 pilot |
| 只围绕两家熟悉公司的短查询 | 模型可能只是在容易的关键词题上表现好 | 开发集增加改写、中文、期间/指标混淆；正式案例按事件/发行人分组保留 |
| 候选数不等于计算预算 | 当前 exact dense 先打分所有 eligible chunks，再截候选 | 记录 eligible 数与实际打分数；不要把 `candidate_limit=100` 描述成“只计算 100 个向量” |

本次源码诊断用**人工构造的非真实 embedding** 验证：一个与唯一文档向量正交的查询仍返回该文档。它仅证明“top-k 不带语义拒答”的实现行为，不是任何真实模型质量结论。上述诊断和本报告不产生新的人工 gold。

## 5. Agent 编排、存储和记忆的选型

当前状态机不是原则上的缺陷。已提交 Proposal 明示了 Python 状态机 fallback；模型能依据工具观察调整下一步，拥有持续的研究状态、核验反馈和执行上限，才是本项目需要证实的行为。换成 LangGraph 不会自动使判断更正确。

LangGraph 的优势主要是图状态 checkpoint、interrupt、故障恢复与相关调试设施。官方文档区分 thread 内 checkpoint 和跨 thread store；后者的长期个性化并非当前项目承诺。当前单机原型可继续用已有状态机和 SQLite。如果要承诺进程崩溃后自动恢复执行、较复杂并行分支或跨进程后台任务，再评估迁移成本。[LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

“保存后能重新打开会话”与“任意指令执行到一半崩溃后能自动无副作用重放”不同；当前验收应按实际能力写。尤其 API 调用、工具调用的重试必须计费/计数，不能因为有 checkpoint 就假定副作用被恰好执行一次。

SQLite 当前使用 WAL、外键、busy timeout 与完整同步，适合单机单用户的研究记录。WAL 支持读写并发但仍只有一个 writer，也不适合把活跃数据库放到跨主机网络文件系统。现阶段无需引入 PostgreSQL；分享演示时提供关闭后的完整导出/副本即可，不能只拷贝正在写入的主 `.db` 而忽略 WAL。[SQLite WAL](https://www.sqlite.org/wal.html)

历史选择是“近期＋词项相关原消息”，不是经过检验的语义长期记忆。应保留当前 scope 作为显式约束，并持续测试：用户更正后旧条件是否失效、跨多轮指代是否正确、重开后是否仍能查到原来的证据和公式。需要语义压缩时，将摘要当索引，回到原始证据作回答，避免摘要逐轮变成未经核验的事实库。

## 6. Critic 与实验设计：保留研究问题，补齐测量

现有 E1 已经合理地把 generic review 与 Structured Critic 定义为两整套检查方案；它们共享请求、证据、规则反馈、模型和资源上限，不能把差异归因于 JSON 输出格式一个因素。`check_rules` 检查引用、显式数字及依赖，源码也明确不做语义蕴含判断。这些界限应继续保持。

还应检查以下内容：

- **语义支持与答案完整性分开评分**：删掉难回答的正确内容不算改进；有引用不等于引用支持结论。ALCE 将正确性和引用质量作为不同评价维度，支持这种分开测量的思路。[ALCE](https://aclanthology.org/2023.emnlp-main.398/)
- **同模型自检的限制**：一个模型的 Researcher 与 Critic 可能共享盲点；第二模型可作为诊断对照，但不能直接充当真值。LLM-as-a-judge 的一手研究记录了位置、篇幅和自我偏好等偏差。[Zheng et al., 2023](https://arxiv.org/abs/2306.05685)
- **随机波动与故障保留**：保存每次模型、提示词、预算、顺序及失败；开发阶段交替两种 review 的先后，正式比较固定方案。有预算时重复运行并报告个案差异；12 案不支撑广泛泛化。
- **E2 的结论边界**：固定流程的上游任务解析同样可能出错，不能把正确解析作为 adaptive 独有的免费输入。当前 paired E2 对 runtime encoder 的限制应明确记录；若暂用 BM25 冻结对照，只能报告该检索配置下的规划比较。
- **截止时间语义**：实时适配器默认缓存不代表当前最新数据。案例应显式区分 replay、缓存和刷新，记录当时可知来源。发布日期仅精确到日时不能伪装成确定的盘中可见时间。

用户当前没有时间标注，不妨先完成代码、开发诊断和自动化运行材料。若以后正式实验仍无法完成独立语义判断，应把相应结果报告为自动诊断/待审核，并调整可支持的研究结论；不能把模型生成的标签改名为“两位组员独立标注”。

本轮整合另修复了两类测量问题：重复检索的耗时/缓存统计不再被算作新研究进展；E1 保存每次实际返回的模型身份并标记漂移，费用按缓存读写等分项处理，旧两单价不能自动成为真实费用下界。相关验收见 [STATUS.md](STATUS.md) 与 [COSTS.md](COSTS.md)。

## 7. 改进顺序与完成条件

| 优先级 | 任务 | 可无人工标注推进的部分 | 完成条件 |
|---|---|---|---|
| P0：本轮 | 模型接口与实际能力描述一致 | provider/JSON 接线、失败保留、调用预算、测试和配置文档 | 不伪装 strict schema 或真实调用；新配置不会改变既有实验而不留记录 |
| P0：本轮 | E3 口径修正 | 区分负例类别、延迟范围、冻结来源及模型信息 | 输出可以读出测到了什么、没有测到什么 |
| P0：本轮 | 本地 embedding 比较 | 同语料开发诊断、设备/版本/内存/延迟记录 | 保存所有候选的结果与失败，不凭名字选最小或最大 |
| P1：随后 | 财报结构保存 | HTML 行列/表头/脚注定位、结构 fixture、块版本管理 | 数字能返回其表头、单位和期间；复杂结构明确失败 |
| P1：随后 | 更强开发检索集 | 中英改写、财务近义概念、负例、块长试验 | 保留开发标签来源，和独立正式数据分开 |
| P1：真实接入后 | 自主多轮 pilot | 自动建会话、运行、保存证据/成本/失败和导出材料 | 使用真实模型完成或诚实失败，具备可追溯日志 |
| P2：由失败驱动 | reranker、PDF、ANN、框架迁移 | 各自可先做小型离线试验 | 观察到相应瓶颈且收益覆盖复杂度，才接入默认路径 |

SEC 已在代码中配置带联系信息的 User-Agent、显式网络开关及进程内限速。官方限制是跨机器合计不超过每秒 10 次请求；因此将来多个进程/机器并发取数时要共享节流，单进程的局部限速不能视作全局保证。[SEC rate control](https://www.sec.gov/filergroup/announcements-old/new-rate-control-limits)

## 8. 最终报告中如何交代与 Proposal 的关系

已提交 Proposal 不需要为了实现细节追溯改写。最终技术报告应给出“原计划 → 实际实现 → 选择理由 → 验证证据”的短表：LangGraph fallback 选择了 Python 状态机；Streamlit/Plotly 改为本地 Web/SVG；主模型仍按实际接入与试验确定；embedding/融合策略以实际测量说明。偏离本身不等于设计失败，**未说明的偏离和没有验证却写成最优选择才会削弱可信度**。

这份复核目前可以支持“为什么保留轻量基础设施、为什么优先改善证据链”的设计决定；不能支持任何模型的最终性能排名。技术选型的下一步证据应来自同条件的可重现测量和实际失败分析。
