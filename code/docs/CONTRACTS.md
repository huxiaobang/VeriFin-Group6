# Shared implementation contract

Baseline: the 9 October 2026 revised Proposal. JSON-serializable dictionaries at module boundaries; Python 3.11+, standard library core. All IDs and timestamps persisted. No company allowlist; replay coverage is finite and explicit. No arbitrary Python evaluation. Every tool/network/model attempt must count toward root runtime budgets, including failure; no silent retries. Root orchestrator owns budgets, state loop and writes returned tools to storage.

## SessionStore (storage.py, owner storage agent)
SessionStore(path) SQLite. Public methods return dict/list values; validation errors ValueError, missing sessions KeyError. close(). create_session(title="Untitled") -> session dict with id, title, scope {}, scope_version 1. get_session(id), list_sessions(), update_scope(session_id, scope) -> session; append_message(session_id, role, content) -> message. put_evidence(session_id, record); put_calculation(session_id, record); put_claim(session_id, record). add_event(session_id, event_dict). get_context(session_id) -> {session, messages, evidence, calculations, claims, reports}; records in lists. save_report(session_id, report_dict) -> saved record with id/version; list_reports(session_id); events(session_id). Persist cancellation: request_cancel(session_id), clear_cancel(session_id), is_cancelled(session_id). All objects session-isolated. Retain old versions and invalidate dependent calculations/claims on changed evidence. Prefer records marked stale over deletion. Transactions/locking prevent lost concurrent writes.

Evidence record: {id, kind (financial_fact/document/market_price), entity, metric?, period_start?, period_end?, unit?, value?, text?, published_at, source_url, locator, snapshot_hash, version?}. Metadata strings explicit; unavailable fields may be null. Calculations: {id, operation, operand_ids, value, unit, formula, entity?, period_start?, period_end?, operand_versions?, scope_version?, stale?}. Claims: {id, text, evidence_ids:[], calculation_ids:[], requirement_ids:[], constraints:{entity?,period_start?,period_end?,unit?,metric?}, asserted_value?, asserted_unit?, scope_version?, status?, stale?}. Requirements: [{id,text}]. Scope is object {entities:[], period_start?, period_end?, cutoff?, metrics:[], requirements:[]} plus optional display text. Scope updates invalidate affected records while preserving prior reports; correctness over broad accidental reuse.

## Structured Critic delivery standard

New reviews require one evidence-specific verdict per claim. The controller stores each verdict with the reviewed claim version. Historical report snapshots retain their original review records.

### What one review delivers

1. **A verdict on each current claim.** Give the claim ID, support status, precise source or calculation references and one short, checkable reason linking the evidence to the proposition. Use the Proposal's Supported, Partially Supported, Insufficient Evidence and Conflicting Evidence statuses. For a mixed claim identify the exact supported clause and the clause still in doubt. Reserve Conflicting Evidence for credible sources that disagree after aligning their scope. If a draft directly contradicts a comparable source, reject the affected assertion and say what the source establishes. The absence of a finding cannot confer Supported status. Store scope, claim and evidence versions with the review on the controller side.
2. **Coverage of each part of the current user request.** Link to the actual reviewed answer sentence or sentences, or name the missing answer. Distinguish complete, partial and unanswered coverage. Use the current question, its resolved references and requested precision. A Planner checklist can omit a subquestion. A correct background fact can remain supported while the requested answer is missing. Numbers mentioned only by the Planner or Critic do not count as delivered. A user asking what a filing establishes can receive a complete answer describing its limits. A user asking for the amount still has a quantitative gap when only the direction is established.
3. **Actionable findings only.** Keep the Proposal's target, issue type, evidence references, missing support and proposed action. For a blocking finding identify the exact clause or subquestion and what would change in the user's answer. Describe the missing datum, wrong period, failed operation or excessive attribution concretely. Suggest the smallest feasible correction. Omit optional editorial advice from the repair queue. The Planner selects the action. The controller decides whether to spend another call.

### What counts as evidence

| Proposition | Minimum basis for a positive verdict |
| --- | --- |
| Reported figure or derived comparison | Identify the relevant table row and period column, or link the calculation whose operands resolve to them. Check metric, scope, units, comparison basis and rounding as applicable. Support a ranking and its magnitude separately when both are requested. |
| Management explanation or analyst inference | Point to the relevant passage and its period. State whether it reports an observation, attributes a cause, quantifies a contribution or permits an inference under stated assumptions. Check material contrary evidence within scope. |
| Limit of a source | Identify the relevant release, table or discussion checked, what it does establish, and the missing information needed for the stronger conclusion. One failed query establishes only what that query returned. |

Record IDs can reference stored cells and spans directly. A broad passage needs a short excerpt or narrower location identifying the relevant words. The review need not copy source pages or reproduce an existing calculation trace. A single verdict can support multiple question parts if the delivered sentence actually addresses each. Local validation checks record identity, dates, arithmetic and version integrity. Language-based warnings should reach the Critic with their triggering text and evidence. Only a reproducible structural contradiction can block a claim without a semantic decision.

### When to deliver, revise or stop

- Deliver once the current questions have reviewed answers, including well-supported limits where they answer the question. A stylistic expansion alone does not reopen review.
- Revise when a specific change can resolve a material defect. If the source is already present, route the work to calculation or targeted wording as appropriate. If material evidence is missing, identify a distinct available source or tool action that could change the verdict.
- When the same finding returns on the same evidence and there is no new viable action, deliver the verified portions and the precise gap. Distinguish unavailable disclosure from a failed read or calculation. Reserve review capacity before starting a revision. On interruption, deliver only review results bound to the applicable draft, question and current sources. Recheck changed claims and dependencies.
